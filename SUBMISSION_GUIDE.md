```
Domain (Сутності та Правила)
   ↑
   ← Application (Сервіси та Контракти)
   ↑
   ← Infrastructure (Реалізації)
   ↑
   ← Console (UI та Організація)
```

### Потік даних (Вертикальний зріз)
```
Введення користувача
   ↓
Меню консолі (ClinicApp)
   ↓
AppointmentService (Бізнес-логіка)
   ↓
Доменні моделі (Перевірка та правила)
   ↓
Інтерфейс репозиторію (Доступ до даних)
   ↓
InMemoryRepository (Постійність)
   ↓
Відповідь → Вивід у консоль
```

## 📝 Примітки для оцінювача

1. **Вертикальний зріз**: Повний потік "Запис на прийом" демонструє:
   - Введення користувача → перевірка → бізнес-логіка → постійність → вивід
   - Працює наскрізь через усі шари архітектури

2. **Інваріанти домену**: Неможливо створити:
   - Owner з невалідною email адресою
   - Pet з негативним/нереалістичним віком
   - Appointment у минулому або без тварини/ветеринара
   - Запобігає невірному стану з першого дня

3. **Відповідність SOLID**: 
   - Сервіси залежать від абстракцій (IAppointmentRepository)
   - Легко замінити InMemory реалізацію на Database

4. **Обробка помилок**:
   - Шар домену: Винятки для інваріантів
   - Шар сервісу: Паттерн Result для правил бізнесу
   - Шар консолі: Зручні повідомлення про помилки

5. **Філософія тестування**:
   - Захист від регресій від Ітерації 1
   - Тести перевіряють валідацію домену, логіку сервісу та крайні випадки
